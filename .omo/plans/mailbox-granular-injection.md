# mailbox-granular-injection - Work Plan

## TL;DR (For humans)

**What you'll get:** Cross-project notes stop being "drop a message and hope the other agent goes idle." A sender can now say *how* it wants a note handled — answer it on the side, add it to the worklist (end or next), hand it to a helper agent, build it and send back a PR, or urgently cut in line — and the receiving project routes each note down that lane automatically, with the receiver still in full control of what it permits. A relay-race end-to-end test (agents passing a cipher sentence through the real mailbox) proves the whole chain works with even the cheapest models.

**Why this approach:** Requests stay advisory — the receiving side is always the authority on what actually runs, which keeps the trust model intact and leaves room for a future central orchestrator without redesigning the wire format. Every lane reuses machinery that already exists and is battle-tested (child sessions, background helpers, the safe message-injection gate), so no new risky session plumbing is invented.

**What it will NOT do:** It will not interrupt an agent mid-thought (urgent notes cut the queue but land at the next safe moment). It will not build the central orchestrator or a dedicated intake agent (both recorded as roadmap). It will not implement cloudhome's side of remote execution — only the request/receipt contract lives here.

**Effort:** Large
**Risk:** Medium - the todo write-path and live multi-session e2e are the two spots where reality can diverge from the SDK's promises; both have explicit verification tasks and fallbacks.
**Decisions to sanity-check:** urgent notes never abort a running turn (queue-jump only); receiver may silently downgrade an over-privileged request to a plain note (with the reason logged); remote answering is refused for questions about unpushed local work.

Your next move: start work (`$start-work mailbox-granular-injection`), or run a high-accuracy review first. Full execution detail follows below.

## Scope
### Must have
- C1 wire vocabulary: additive-optional `requested_mode` envelope field with canonical kebab-case enum `["answer", "todo-append", "todo-next", "subagent", "worker-pr", "interrupt"]`; absent field = legacy behavior (main-session triage). Parse path becomes tolerant of unknown keys (future additive fields must not break old parsers); serialize path validates known fields strictly.
- C1 send surface: `requested_mode` argument on BOTH `project_message` and `project_note` tools, threaded through envelope-builder and recorded in the outbox log (`requested_mode` + later `effective_mode` on fulfillment records).
- Mode permission gating (receiver-authoritative): mode→required-tier map (`answer`→question, `todo-append`/`todo-next`/`subagent`→impl, `worker-pr`/`interrupt`→plan) checked against the existing per-sender `intent_budget` ceiling, plus optional per-sender `allowed_modes` allowlist in config. Insufficient budget ⇒ DOWNGRADE to main-session triage with recorded reason — never a hard reject of an otherwise-valid note.
- C6 intake router: pure `decideRoute(note, config, presenceCtx) -> RouteDecision` (deterministic, no I/O) + router execution in the idle-drain hook with injected lane ports; static triage prompt remains the legacy/fallback lane. Manual drain (`project_mailbox_drain`) stays raw-return but surfaces `requested_mode` + per-mode guidance in its output.
- C2 side-session Q&A lane: `answer` notes fulfilled in a fresh child session (`client.session.create({ parentID })`, background-agent spawner pattern); answer sent back as a threaded mailbox reply; note acked into `processed/` at lane completion so `inReplyToMessageId` threading works (envelope-builder requires parent in processed/).
- C3 todo-injection lane: `todo-append` and `todo-next` mutate the ACTIVE session's todo list via the verified SDK write route (spike decides between `client.session.todo` write and the `Todo.update` route used by compaction-todo-preserver), with boulder-state (`addBoulderWork`) as the durable fallback when no live session exists.
- C4 subagent lane: `subagent` notes dispatched as background task(s) — single subagent, or investigate→implement pair when the note requests it — via the existing task/background-agent surfaces; completion reported back as a threaded reply note.
- C5 worker-PR lane (local substrate): work-order file written into a task-owned git worktree of this repo + headless worker launched against it (extends `launchTargetSession`); branch naming `omo/mailbox/<messageId>`; worker output = PR whose URL is reported back as a threaded reply note for main-session intake. PLUS the declared `worker=cloudhome` variant: request-contract payload + pending state + PR-intake handling only (cloudhome-side execution is out of scope, delegated via project_message).
- C2c cloudhome-hosted answer variant (contract side only): when no local presence AND note flagged not-in-flight-local, emit a remote-answer request record and report `pending`; intake of the remote answer threads like a local one.
- C7 safe interrupt lane: `interrupt` notes are delivered through the external-inject bridge (queue-jump: dispatched immediately rather than waiting for the drain poller) + todo-PREPEND (`todo-next` semantics forced to top). Explicitly NOT a mid-turn abort: injection still lands at the prompt-async-gate's next safe boundary.
- Classifier subagent: only for notes with NO `requested_mode` and ambiguous intent; cheap model category; output constrained to the canonical mode enum.
- C8 cipher-relay e2e harness: sandbox project generator, per-project private cipher fixture files (project i owns numbers 10i..10i+9), arbiter script validating the completed sentence, runner with wall-clock time limit; isolated XDG sandbox + alternate opencode DB + OpenRouter free models (memory #1746 conventions).
- Config schema additions (`allowed_modes`, downgrade policy), `bun run build:schema` regen, docs updates, roadmap note (orchestrator phase: sender requests → orchestrator decides → receiver follows; dedicated intake agent).
- TDD (bun:test, given/when/then) for every module; opencode-qa isolated-sandbox evidence for every harness-connected change under `.omo/evidence/`.

### Must NOT have (guardrails, anti-slop, scope boundaries)
- NO orchestrator implementation and NO dedicated intake agent (roadmap-only notes).
- NO mid-turn abort/steering of a live OpenCode turn; interrupt = queue-jump + todo-prepend only.
- NO raw `session.prompt`/`session.promptAsync` outside `dispatchInternalPrompt` (inline object literal with `queueBehavior` — static audit #584/#2094 must stay green).
- NO cloudhome-side implementation — only the request/PR-intake contract half in this repo; the cloudhome half is delegated via project_message.
- NO openclaw integration in the critical path.
- NO breaking change for CURRENT-version peers: `requested_mode` optional; absent ⇒ exact legacy behavior; parse tolerance change covers future additive fields. (Do NOT claim old-version receivers accept the new field — they strict-reject; all local peers run this same plugin build, and the tolerant-parse change is the durable fix going forward.)
- NO new top-level mode-selection authority: receiver stays authoritative; `requested_mode` is advisory.
- NO `mock.module` at module top level (memory #2177); dependency-inject ports instead.
- NO catch-all files; 200 LOC soft limit; kebab-case; barrel exports only.
- NO MVP/scope reduction of C1–C8.
