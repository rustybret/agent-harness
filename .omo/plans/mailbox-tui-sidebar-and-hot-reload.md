<!-- Plain English for a non-engineer: NO file paths, NO todo numbers, NO wave/agent/tool names. -->

**What you'll get:** Your terminal sidebar gains a Mailbox panel that shows, at a glance, how many cross-project notes are waiting for you to read and how many notes you sent are still unread by the other project — and you can click its header to fold it away, just like the Magic Context and AFT panels. Separately, you can change which projects may message you (or how much they may ask for) by editing one config file, and both sessions pick up the change on their next message or idle moment — no restart.

**Why this approach:** Cross-project messaging becomes always-available (the tool and the background pickup are always wired in), and you turn a project "off" simply by granting it no permissions, which removes the old need to restart to flip an on/off switch. "Read by the other project" is detected from the acknowledgement the receiving project already writes to disk when its idle session picks the note up.

**What it will NOT do:** It will not interrupt a session you are actively typing in (notes still wait for an idle moment). It will not track whether the other project finished the work — only whether it read the note. It will not watch the config file in the background; it re-reads it the next time it sends or goes idle.

**Effort:** Medium
**Risk:** Medium - flipping cross-project messaging to on-by-default changes behavior for every project that uses this fork; mitigated by a permissionless "off" state and a cheap no-op when a project has no senders.
**Decisions to sanity-check:** on-by-default for all projects (off = no permissions); "read" means picked-up-by-idle, not task-done; rejected notes shown as a distinct failed state; collapse state shared in the same preferences file AFT/Magic Context use.

## Scope
### Must have
- A Mailbox section in omo's TUI sidebar showing UNRESOLVED inbound (notes others sent me, not yet drained) and UNRESOLVED outbound (notes I sent, not yet read by the destination).
- Outbound resolution is 3-state per sent note: **read** (destination wrote it to its `processed/`), **failed** (destination wrote it to its `rejected/`), **sent/unresolved** (neither yet). "Unresolved outbound" = sent-not-yet-read-or-failed.
- A ▶/▼ click toggle on the Mailbox header (opentui `onMouseDown`) that expands/collapses the section, mirroring Magic Context / AFT; collapse state persists across restarts in the shared `~/.config/opencode/tui-preferences.jsonc` under top-level key `"oh-my-openagent"`.
- The section renders in BOTH the `active` and `idle` sidebar views (a project can have mailbox signal with no agents/jobs/loop running).
- P1: editing a project's `.opencode/oh-my-openagent.jsonc` `cross_project_mailbox` (senders, default_sender_access, intent budgets, bounds) takes effect WITHOUT restarting either session — the `project_message` send and the idle-drain both re-read the merged config per operation.
- Schema/loader fix so `enabled` no longer needs a mid-session flip: the ROOT `cross_project_mailbox` field STAYS optional in the schema (so an omitted block never clobbers a farther layer's explicit value during the shallow per-layer merge), and the merged-config LOADER injects a populated default object (`enabled:true`, `default_sender_access:"allow-none"`, empty `senders`) ONLY when the fully-merged block is undefined. Result: the tool + idle-drain always register; "off" is emulated by `allow-none` + empty `senders`; an explicit `"enabled": false` anywhere survives the merge as an honored hard-off (no registration).
- TDD for every code todo; a LIVE opencode-qa harness run proving the sidebar, the toggle, the sent→read transition, and a no-restart permission change, with evidence under `.omo/evidence/<date>-mailbox-tui-hot-reload/`.

### Must NOT have (guardrails, anti-slop, scope boundaries)
- NO `allow-interrupt` / preemption of an active session — idle-drain delivery semantics are unchanged.
- NO `fs.watch` on the config — reload is lazy per-operation only (the chosen Q3 option).
- NO bespoke single-file JSONC parse for the hot-reload — it MUST reuse the existing READ-ONLY merged-config loader `validatePluginConfig(directory)` (config/validate.ts) so user-config + walked project configs + legacy basenames + merge semantics are preserved. Do NOT use the runtime `loadPluginConfig` on the hot-path — it can MIGRATE legacy config files (side effects) on every send/drain.
- NO `.default()` on the ROOT `cross_project_mailbox` schema field — per-layer parse + shallow merge (config-merger.ts:8-10 spreads `...override`, mailbox is NOT deep-merged) would let a nearer defaulted block clobber a farther explicit `enabled:false`. The populated default is injected ONCE post-merge.
- NO raising the effective body cap above the envelope hard limit — `serializeEnvelope` throws at `MAX_BODY_BYTES=32768` (envelope/schema.ts:6,32) regardless of config; the effective cap is `min(bounds.max_body_bytes, 32768)`, so a config value above 32768 is a documented no-op.
- NO unbounded outbox scan — outbound ack resolution is limited to a bounded recent window of sent entries.
- NO raw `session.promptAsync` — the idle-drain stays on `dispatchInternalPrompt`; the prompt-async-route-audit must stay green.
- NO change to the registry hot-path (it is already re-read per send/drain).
- NO emojis, no AI-slop comments, no `as any`/`@ts-ignore`, 200 LOC soft cap per file, kebab-case files, given/when/then tests.
- Do NOT auto-migrate users' existing explicit `"enabled": false` configs to true (honor their hard-off); only the auto-provision stub and the schema default change.
