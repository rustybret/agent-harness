# unity-supermcp-subagents - Work Plan

## TL;DR (For humans)
<!-- Fill this LAST, after the detailed plan below is written, so it summarizes the REAL plan. -->
<!-- Plain English for a non-engineer: NO file paths, NO todo numbers, NO wave/agent/tool names. -->

**What you'll get:** Two competing ways to hand Unity editor work to a fast, locked-down AI helper — one generalist that picks its specialty per request, and six specialists with one specialty each — plus a head-to-head test procedure to decide which design wins on your real game project. The helpers can only talk to the Unity bridge; they cannot touch files, run shell commands, or wander off-task.

**Why this approach:** The existing Unity helper configuration was silently broken (written in a format the system never reads), so everything is rebuilt on the format that actually loads, with the restriction enforced by the platform itself rather than by trusting the AI's instructions. The specialist knowledge files are copied into this repo with a one-command refresh so both sides stay in step.

**What it will NOT do:** It will not run anything against your live Unity editor by itself — the head-to-head test only happens when you say go. It will not change the plugin's core model-routing code. It will not promote the Unity bridge into the always-on tool set.

**Effort:** Medium
**Risk:** Medium - the permission lockdown and fast-model dispatch behavior are proven only in sandbox QA; live-editor behavior is deliberately deferred to the gated benchmark.
**Decisions to sanity-check:** Six specialists share one name with their matching knowledge files (deliberate, documented); the cheapest usable model leads the chain with heavier ones as fallbacks; the old broken helper file is deleted, not kept.

Your next move: dual high-accuracy review runs automatically (you asked for it), then $start-work unity-supermcp-subagents. Full execution detail follows below.
