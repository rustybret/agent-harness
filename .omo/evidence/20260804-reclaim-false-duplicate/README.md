# Reclaimed notes were quarantined as duplicates of their own failed attempt

## How this was found

Dogfooding the delivery-status mode shipped earlier the same session (`f238d0668`). Running it
against this repo's real outbox reported **18 rejected out of 38 sent notes - a 47% rejection rate**,
every one of them `duplicate-loop`. That is exactly the "did this ever land" uncertainty cloudhome
described; the status tool made a long-standing silent failure visible in one call.

Inspecting the quarantined notes in the targets' mailboxes showed all of them had **distinct**
correlationIds and **distinct** body hashes. By the digest key
(`from:to:correlationId:sha256(body)`) they were not duplicates of each other at all.

Every `.reason.json` written by any target for notes from this project: 10 of 10 `duplicate-loop`.

## Root cause

Two TTLs that must agree, and do not:

| | default | governs |
|---|---|---|
| `reservation_ttl_ms` | 120 000 (2 min) | how long a delivery reservation is held |
| `body_digest_ttl_min` | 60 (60 min) | how long a body digest suppresses duplicates |

A note records its body digest when a delivery attempt begins. If the attempt never confirms - the
dispatch was rejected, the session went away, the process died - `reclaimStale` returns the note to
the inbox for a retry. It did **not** release the digest.

Because the digest outlives the reservation by 30x, the retry is guaranteed to hash to the same key
inside the TTL and be quarantined as `duplicate-loop`. The note is rejected as a duplicate of its
own failed attempt, and the sender is told its message was a loop.

Note the shape: this is the mirror of `59ec994fd`, which fixed the same missing rollback on the
`fallback-next-drain` path. The reclaim path had the identical hole.

## What was tested

`drive.mjs` uses the REAL `MailboxStore` and the REAL `BodyDigestStore` against a temp repo:

1. Write a note, drain it, reserve it, record its digest - then never confirm the dispatch.
2. Age the reservation past its TTL and run `reclaimStale`.
3. Drain again and re-run the duplicate check, exactly as the drain hook does.

## What was observed

| | `reclaim` reports returned ids | retry duplicate check | outcome |
|---|---|---|---|
| before | no (returns `void`) | `true` | quarantined `duplicate-loop` |
| after | yes (1 id) | `false` | redelivered |

Full captures: `before-reclaim-redelivery.json`, `after-reclaim-redelivery.json`. Before-capture
taken by reverting only `mailbox-store.ts` via `git stash`, re-running the same driver, then
restoring - byte-identical restore verified with `cmp` (`RESTORED-OK`).

## Why this is enough

`reclaimStale` now reports which ids it returned to the inbox, as opposed to the ones it acked
because delivery turned out to have succeeded, and the drain hook releases the digest for exactly
those. Both directions are pinned:

- `mailbox-store.test.ts` - the 4 existing reclaim cases now also assert the returned ids: the two
  acked cases report `[]`, the two returned-to-unread cases report the message id.
- `idle-drain-hook.test.ts` - a reclaimed note has its digest rolled back before the duplicate
  check and still dispatches; a note that was NOT reclaimed keeps its digest, so a genuine resend of
  identical content inside the TTL is still suppressed.

Full suite green (13774 pass / 0 fail), typecheck clean.

## What was omitted

No secrets or credentials are involved. The driver runs entirely in a `mktemp` directory it removes
on exit. Message ids in the captures are generated by the driver, not real traffic.

Not fixed here: the 18 already-quarantined notes stay quarantined - this prevents recurrence rather
than replaying history. Also unaddressed is the TTL mismatch itself; releasing the digest on reclaim
makes the two consistent in behavior, but a note reserved and abandoned WITHOUT reclaim running
(e.g. the repo is never opened again) still holds its digest for the full 60 minutes.
